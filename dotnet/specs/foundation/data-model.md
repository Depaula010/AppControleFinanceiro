# Modelo de dados

Reconstruído do dump `migrations/schema.sql` (HeidiSQL, PostgreSQL 15.15, **17/03/2026**) cruzado com o código (commits até 07/09/2026). A estrutura exportada de produção está em `schema-prod.sql` (mesma pasta; HeidiSQL, 2026-10-02, sem dados, com os triggers acrescentados à mão). Em caso de divergência, vale o `schema-prod.sql` e as consultas de §6.

> `migrations/schema.sql` contém dados reais (hash de senha, chave de API, sessão do bot). Está fora do git (`.gitignore:125`) e **nunca** deve ser commitado ou compartilhado.

## 1. Premissas que mudam tudo

1. **Os nomes reais são minúsculos e sem aspas.** O SQL cru do Python usa identificadores sem aspas (`FROM Contas`), que o Postgres dobra para minúsculas. Tabelas: `usuarios`, `contas`, `transacoes`, `subcategoria`, `potesdegastos`...
2. **ORM do Python, `adapters.py`, três `.sql` soltos e a migração Alembic `99422c2605c6` usam aspas e maiúsculas** (`"Usuarios"`). Estão mortos ou quebrados contra o banco real. Não são fonte de verdade.
3. **Sem soft delete em transações**; soft delete em `contas.ativa` e `agendamentos.ativo` (nomes diferentes!).
4. **Valor com sinal**: despesa negativa, renda positiva. Saldo = `saldo_inicial + SUM(valor)`; não há coluna de saldo.
5. **Multi-tenant por linha**: `usuario_id = :uid` em quase tudo; sem RLS. Categorias globais têm `usuario_id IS NULL`.
6. **O bot Node compartilha o banco** (`baileys_auth`). O .NET não pode alterar essa tabela além do `DELETE` de `/admin/clear-bot-session`.

### contas

Constraints: UNIQUE(usuario_id, nome_conta) (vale para inativas também; a API só checa entre ativas); `chk_cartao_credito` (dias só existem se tipo = cartão).

### faturas

### transacoes

### agendamentos

## 3. Relacionamentos

```
usuarios 1─N contas 1─N faturas
   ├─ conta_padrao_{renda,despesa}_id ─► contas (SET NULL; FK circular)
   ├─1─N transacoes ─► contas(RESTRICT) · subcategoria(RESTRICT) · faturas(SET NULL)
   │                    · agendamentos(SET NULL) · transacoes(par, SET NULL)
   ├─1─N agendamentos ─► contas(CASCADE) · subcategoria(RESTRICT)
   ├─1─N potesdegastos ─N:N─ subcategoria
   ├─1─1 notificationconfigs · monthlyreportconfigs · calendaralertconfigs · googlecalendartokens
   ├─1─N enderecosfavoritos · chavesapiusuario · preferenciaschaveapi · logacessochaveapi
   │      · rastreamentousoapi · consentimentousuario · assinaturasusuario ─► planos
grupocategoria 1─N macrocategoria 1─N subcategoria   (usuario_id NULL = global)
```
Tudo que pende de `usuarios` é CASCADE, exceto `transacoes.conta_id` (RESTRICT).

## 4. Estratégia EF Core + Dapper

| Uso | Ferramenta |
|---|---|
| CRUD de usuarios, contas, agendamentos, configs, chaves, endereços, upserts (`ON CONFLICT`) | EF Core (`ToTable("usuarios")`, `HasColumnName` explícito; sem convenção por pluralização) |
| Relatórios/dashboards, check-in noturno, faturas a fechar, forecast, gráficos | Dapper com SQL portado |
| `UPDATE ... WHERE id = ANY(@ids)` | Dapper (array nativo do Npgsql) |

Pontos de atenção no mapeamento:
- `date` ⇒ `DateOnly`, `time` ⇒ `TimeOnly`, `timestamptz` ⇒ `DateTime` UTC (Npgsql 6+ rejeita Kind ≠ Utc), `monthlyreportconfigs.*_at` é `timestamp` sem tz.
- PK composta (`baileys_auth`) e PK = FK (`monthlyreportconfigs`).
- FK circular `usuarios ↔ contas` e auto-FK em `transacoes`: configurar `OnDelete` explícito e inserir em duas etapas.
- Triggers `BEFORE UPDATE` mantêm `updated_at` (função `update_updated_at_column()`); marcar `ValueGeneratedOnAddOrUpdate` e **não** definir no código.
- `(:p IS NULL OR col = :p)` exige cast do parâmetro no Npgsql (`@p::date`).
- Mistura identity/serial: scaffold resolve; não recriar sequences.
- `TO_CHAR(..., 'Day')` depende de `lc_time` do servidor; decidir por formatar o dia da semana no código (desvio 009).

## 6. Resultados da inspeção da produção (2026-10-02)

Fonte: `scripts/homol/heidisql/01-inspecao-producao.sql` rodado por Rafael. Consultas 1–10 e as constraints de `transacoes`, `usuarios`, `notificationconfigs` e `potesdegastos` recebidas; as consultas 11 a 15 também foram respondidas. **Todas as consultas da inspeção estão concluídas.**

**Ambiente:** PostgreSQL 15.15 (Alpine), `TimeZone = UTC`, `lc_time = C`, Alembic em `99422c2605c6`.

**Volume (tudo muito pequeno): 1 usuário, 4 contas, 38 agendamentos, 12 faturas, 330 transações (300 `Despesa` + 30 `Renda`, nenhuma `Receita`), 61 subcategorias, 18 macros, 5 grupos, 3 planos, 3 chaves de API, 11 linhas de uso.** `baileys_auth` tem 3234 linhas (bot). Vazias: `assinaturasusuario`, `consentimentousuario`, `logacessochaveapi`, `monthlyreportconfigs`, `potesdegastos`, `potesubcategorias`. Consequência: o risco real da virada é de comportamento, não de volume de dados.

**Confirmado:**
- **Identity** (`GENERATED ... AS IDENTITY`): `agendamentos`, `contas`, `enderecosfavoritos`, `faturas`, `potesdegastos`, `potesubcategorias`, `transacoes`, `usuarios`. **Serial** (`nextval`): todas as demais.
- **Triggers** `BEFORE UPDATE` com `update_updated_at_column()` (`NEW.updated_at = CURRENT_TIMESTAMP`) em 9 tabelas: `agendamentos`, `contas`, `faturas`, `grupocategoria`, `macrocategoria`, `potesdegastos`, `subcategoria`, `transacoes`, `usuarios`. **Não** há trigger em `notificationconfigs`, `calendaralertconfigs`, `googlecalendartokens`, `enderecosfavoritos` (nem nas tabelas de chaves): nessas o código deve gravar `updated_at`.
- **CHECKs vistos:** `agendamentos` (dia 1–31, mês 1–12 ou nulo, periodicidade, tipo, `chk_anual_mes`, `chk_parcelado`), `contas` (`chk_cartao_credito`, dias 1–31, `tipo_conta` nas 6 opções), `faturas.status`, `enderecosfavoritos.label`, `calendaralertconfigs.chk_minutos_antes`.
- **UNIQUE vistos:** `contas(usuario_id, nome_conta)`, `faturas(conta_id, data_vencimento)`, `enderecosfavoritos(usuario_id, label)`, `chavesapiusuario(usuario_id, provedor)`, `preferenciaschaveapi(usuario_id, provedor)`, `consentimentousuario(usuario_id, tipo, versao)`, `usuarios(numero_whatsapp)`, `usuarios(email)`, `usuarios(api_key_automate)`, `subcategoria(macro_id, nome_sub, usuario_id)`, `potesdegastos(usuario_id, nome_pote)`, `potesubcategorias(pote_id, subcategoria_id)`, `grupocategoria(nome_grupo)`, `planos(nome_plano)`.
- **Índices parciais:** `idx_agendamentos_reserva (usuario_id, incluir_na_reserva, periodicidade) WHERE ativo`, `idx_chaves_api_ativo WHERE ativo`, `idx_consentimento_ativo WHERE consentimento_dado AND revogado_em IS NULL`, `idx_usuarios_meses_reserva WHERE meses_reserva_emergencia IS NOT NULL`. Logs com `timestamp_acesso DESC` e `mes_ano DESC`.
- **`usuarios`** tem 3 colunas "padrão de conta" (`conta_padrao_renda_id`, `conta_padrao_despesa_id`, `conta_padrao_id`) e `ativo`, `ultimo_acesso`, `fuso_horario` (já refletidas acima).
- **`notificationconfigs`** perdeu colunas (posições 3, 4, 7, 8 e 9 não existem): `agenda_diaria_*` foram removidas de propósito.
- **`api_key_automate`** (consulta 11): o único valor é texto puro de 40 caracteres, sem prefixo Fernet. A coluna `varchar(100)` não comporta um token Fernet (desvio 017). O .NET precisa aceitar texto puro na leitura.
- **Tokens do Google** (consulta 12): `access_token` e `refresh_token` em texto puro, sem Fernet (desvio 029).
- **Subcategoria global duplicada** (consulta 13): `Outros` aparece 2 vezes em `macro_id = 17` (desvio 030); buscas por nome devem ordenar por `id`.
- **Colunas ausentes** (consulta 14, resultado vazio): nenhuma das 11 colunas consultadas existe, confirmando os desvios 027 e 028.
- **`budgetviolations` não existe** (consulta 15): não migrar; `/admin/setup-budget-violations` vira no-op (desvio 002).
- **Hash de senha:** o único usuário tem `scrypt:32768:8:1`. **O .NET precisa verificar scrypt para logar o usuário real**; pbkdf2 só é necessário para novos cadastros.
- **`lc_time = C`** ⇒ `TO_CHAR(..., 'Day')` devolve inglês com padding (desvio 009).
- **`transacoes_tipo_transacao_check`** (lido): aceita só `Renda`, `Despesa`, `Transferência`, `Pagamento Fatura`; sem linhas `Receita` (desvio 001 confirmado).
- **FKs de `transacoes`** (lidas): `usuario_id` CASCADE, `conta_id` RESTRICT, `subcategoria_id` RESTRICT, `fatura_id` SET NULL, `transferencia_par_id` SET NULL, `agendamento_id` SET NULL (`fk_transacoes_agendamento`). `usuarios`: `conta_padrao_renda_id`, `conta_padrao_despesa_id` e `conta_padrao_id` (`fk_usuarios_conta_padrao`) SET NULL.
- **Sem CHECK** em `notificationconfigs` (não existe `chk_checkin_hora`): o limite 18–23 do check-in vale só no código. `potesdegastos.periodicidade` aceita SEMANAL, QUINZENAL, MENSAL, ANUAL.

**Colunas que o código usa e NÃO existem** (confirmadas ausentes): `transacoes.observacoes` e `transacoes.origem` (desvio 027); `notificationconfigs.agenda_diaria_*`, `usuarios.whatsapp_numero`, `planos.limite_mensal_*`, `consentimentousuario.versao_termos/ip_endereco/user_agent`, `logacessochaveapi.data_acesso` (desvio 028).
